## 二、为什么这样改

原版提醒只有一句 `AlarmManager.setAndAllowWhileIdle`，不落盘，类注释自己写着 `Reboot clears the alarms (no persistence yet)`。重启后系统清空闹钟，App 也没有开机重排，提醒会全丢。

所以三件事必须同时有，缺一件都不成立：

1. 事项落盘 `tasks.json`
2. 每天四个时点扫描
3. 开机广播重排

## 三、数据

```
/sdcard/Android/data/dev.xiaoman.app/files/tasks/tasks.json
/sdcard/Android/data/dev.xiaoman.app/files/tasks/archive/YYYY-MM.md
```

一条事项：

| 字段 | 说明 |
|---|---|
| `bed` / `name` | 显示用，床号可改 |
| `patientKey` | 归属键，默认姓名；调床不变，不会串人 |
| `item` | 要确认什么，如"术前检查" |
| `note` | 用户原话，原样保留 |
| `rule` | `daily`（每天四时点）或 `monthly`（每月 N 号） |
| `anchor` | 空 / `surgery+N` / `discharge` / `date` |
| `state` | `active` / `done` / `expired` |
| `until` | 有效期，过期不再推 |
| `silentDate` | 当天说"看过了"的日期 |

## 四、五个工具

| 工具 | 作用 |
|---|---|
| `task_add` | 批量建，一句话拆多条 |
| `task_list` | `today` / `all` / `expired` / `bed` |
| `task_done` | 按 id 或 床号+关键词 关闭 |
| `task_update` | 调床、延期、记手术日/出院日、当日静默 |
| `task_roster` | 用 HIS 表里的床号+姓名核对：同名换床直接改，同床异名/同名多人只报告 |

## 五、提醒规则

- 08:00 / 11:00 / 14:00 / 17:00 各一次，聚合成一条通知
- 没回应 → 下一个时点继续
- 说"看过了" → 当天剩余时点跳过，次日恢复
- 说"办完了" → 关闭
- 到锚点当天：术前事项由助手关闭，术后事项带 `anchorDate` 后开始计时
- 过期不推，但在 `task_list(expired)` 单列"已过期未确认"

| 类型 | 默认 |
|---|---|
| 待手术 | 手术日；不知道就 30 天 |
| 查血 / 复查 | 目标日 +5 天 |

| 月度上报 | 当月最后一天 |

## 七、DeepSeek 与图片

- Base URL：`https://api.deepseek.com/v1`（已设为默认）
- 聊天模型：`deepseek-flash`（已设为默认）。**踩过的坑**：`deepseek-v4.1-flash` 是模型宣传名，接口会回 400 `Model Not Exist`；官方 id 是 `deepseek-flash`，`deepseek-chat` / `deepseek-v4-flash` 是兼容别名
- 深度思考：请求体带 `thinking: {type: disabled}`（只对 `deepseek` 域名发，别的兼容服务会拒未知字段）。开着时延迟十几秒、多花思考 token，且 temperature 失效
- Temperature：留空按 0.2 发，不是服务商默认的 1.0
- 多模态：`OpenAiCompatibleClient.encodeMessage` 按 OpenAI 格式发 `image_url`（base64 data URI，mime 跟着字节走）
- 图片入口：聊天框左侧按钮 → 系统照片选择器 → 脱敏确认 → 发送；照片先经 `ImagePrep` 压到长边 1024 / JPEG 85
- 图片生命周期：只在当前这一轮请求里；工具多轮循环内会重发，历史只存「（附图 N 张）」文字，不重复计费
- 操作模型：可留空。留空时 `phoneTasks=false`，不提供 `phone_task`；填了就按读屏模型使用
- 原版要求两个模型都配置才启动，这里改成只要聊天模型

## 八、已知限制

1. `setAndAllowWhileIdle` 在深度休眠下可能延迟几分钟，不是秒级精确
2. 归档只在 App 启动时检查，不启动就不会归档
3. 月份里没有 30 号时（如 2 月），`monthly` 的 30 号不会补推
4. 同名同姓两位患者需要助手追问区分，第一版靠姓名做键
5. 提醒内容是助手按模板组织的，不生成医嘱，也不写回任何病历系统
6. 图片是整包发到云端模型的：脱敏确认只能靠人，代码不会自动识别人脸或姓名，也不会拦截
7. 一轮对话最多带 1 张图（界面没有多选），压缩后不保留原图，发完即丢
8. 模型不支持图片时，请求会被服务端拒绝，只报错不降级
8.1 `测试连接` 只发一句纯文本，所以它能证明「Key/模型名/网络」没问题，不能证明「图片能用」
9. HIS 核对必须带姓名，这张图的姓名一定上云，和「发照片」的脱敏提醒天生冲突；要彻底不上云，得改成端上 OCR + 端上比对，那是另一条工程路线
10. `李**` 这类遮挡姓名只能按前缀匹配；两位同姓同遮挡的患者会被判成「同名多人」，需人工指定
11. 只在「同名换床」这一种情况下自动改床号，同床异名和查无此人一律不动

## 九、开机与后台

- `BootReceiver` 接收 `BOOT_COMPLETED` 和 `MY_PACKAGE_REPLACED`，重排四个时点；重启不丢提醒
- 不常驻后台：AlarmManager 的 PendingIntent 由系统持有，进程被回收也能唤醒
- 前提是系统允许自启动、电池不限制；国产 ROM 默认会拦，"强行停止"会取消所有闹钟
